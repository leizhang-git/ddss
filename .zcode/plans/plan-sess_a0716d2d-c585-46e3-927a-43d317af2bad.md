## 目标架构全景

```text
Vue 3 + TypeScript 前端
  页面/路由 → feature 用例与状态 → 生成的类型化 API 客户端
                                      │ HTTP / OpenAPI
                                      ▼
┌────────────────────── ddss-bootstrap ──────────────────────┐
│ Spring Boot composition root：配置、DI、安全、日志/指标/trace │
└──────────────────────────────┬─────────────────────────────┘
                               ▼
┌──────────────────── inbound-web adapter ──────────────────┐
│ REST controller、请求/响应 DTO、验证、HTTP 错误映射         │
└──────────────────────────────┬─────────────────────────────┘
                               ▼
┌──────────────────────── application ──────────────────────┐
│ 用例、命令/查询、事务边界、端口、显式结果类型               │
└──────────────┬───────────────────────────────────┬────────┘
               ▼                                   ▼
┌──────────────────────── domain ────────────────────────────┐
│ 纯 Java：Finance/System/Workflow 等领域模型、值对象、规则    │
│ 不依赖 Spring、MyBatis、Flowable、Web、Redis 或序列化框架    │
└────────────────────────────────────────────────────────────┘
               ▲                                   ▲
               │                                   │
┌──────────────┴────────────────┐  ┌─────────────┴──────────┐
│ outbound-persistence adapter  │  │ engine/messaging/cache │
│ MyBatis、SQL、ORM 映射、事务   │  │ Flowable、Kafka、Redis │
└───────────────────────────────┘  └────────────────────────┘

编译依赖方向：domain ← application ← inbound/outbound adapters ← bootstrap
前端只依赖公开 HTTP 契约，不依赖数据库实体；所有运行时依赖在 bootstrap 组合。
```

建议将当前五个 Maven 模块收敛为 `ddss-domain`、`ddss-application`、`ddss-adapter-web`、`ddss-adapter-persistence`、`ddss-adapter-workflow`（及确有需要的 messaging adapter）和 `ddss-bootstrap`。按 system、finance、video、workflow、scheduler、generator 等领域组织包，而不是把“common/framework/provider”当业务边界。当前共有模块与框架模块的具体归属会在迁移中逐项核验，避免保留新的万能共享模块。

## 原工程的架构级罪状（按代码证据）

1. **所谓领域/契约模块带着框架进场。** `ddss-common` 依赖 Spring Security、Redis、Servlet、PageHelper，`LoginUser` 实现 `UserDetails`；`ddss-consumer` 又依赖 MyBatis-Plus 和数据源注解，因此模块链只是物理拆分，并未形成技术中立的领域边界。
2. **端口和适配器的位置放反了。** REST resource、ServiceImpl、MyBatis XML、Flowable 逻辑都集中在 `ddss-provider`，而 `ddss-bootstrap` 主要是入口和少量控制器；`WorkflowTaskServiceImpl` 直接依赖 Flowable 和 QueryWrapper，外部引擎没有端口隔离。
3. **同一个可变 JavaBean 同时扮演 API、领域和数据库模型。** `SysUser`、`SysFinance`、`DdssLeave` 等携带 ORM/请求联结数据和开放 setter，领域语义被框架绑定与传输形状掩盖。
4. **万能响应与无形契约并存。** 可变 Map 型 `AjaxResult`、泛型 `R<T>`、`TableDataInfo` 三套响应交错，Finance 服务还公开 `Map<String,Object>`；编译器无法保护客户端与服务端的数据结构。
5. **依赖由运行时魔法隐藏。** 字段注入和 `SpringUtils.getBean` 出现在服务、异步和 Quartz 代码中，实例创建不自描述，核心逻辑也难以脱离 Spring 测试。
6. **错误语义不稳定。** 业务异常有的带 ErrorCode、有的只有字符串；工作流若干 catch/rethrow 丢弃 cause，分页又混合 ThreadLocal PageHelper 和独立 `WorkflowPage`。
7. **并发工具多于并发语义。** `KafkaProducer` 自建队列、轮询、sleep 与退出标志，异步边界散落；虽有 MDC 传播，但没有一致的业务事件/失败语义。
8. **工作流及前后端契约确有错误，不是风格争论。** UI 允许半天而后端与 SQL 用整数；UI 批量删除把 ID 拼成一个字符串但服务按单个 ID 处理；上传配置、模型发布与固定 `leaveDemo` 启动流程彼此割裂。
9. **前端页面负担过重、客户端类型不设防。** Vue 2 页面内混合 API、编辑器生命周期、导入导出和提示逻辑；工作流设计器尤甚，部分异步加载失败后 loading 不复位。
10. **质量门禁不足以支撑全局重构。** 后端只找到 Finance 计算器 3 个测试，前端没有测试脚本；架构边界、HTTP 契约、Flowable 状态转换都没有自动验证。
11. **说明文档失真。** `docs/开发参考文档.md` 仍引用已不存在的 `ddss-server` 路径；开发登录开关虽默认关闭，但授权逻辑可授予管理员身份，配置边界需更强约束。

## 实施路线

1. **建立可验证基线。** 记录当前 Maven/前端构建结果、模块依赖、API 路由、数据库表和关键流程；把现有可运行行为作为重构校验清单，避免先搬文件再猜行为。
2. **先立新模块与依赖护栏。** 拆出纯 Java domain、无 Spring 的 application/use case 与 ports，再建立 inbound/outbound adapters 和唯一 composition root；加入 Maven Enforcer/ArchUnit 规则禁止 domain/application 引入框架和 adapter 互相依赖。
3. **按垂直业务切片迁移所有后端领域。** 依次处理 finance、system/security、workflow、video、scheduler、generator：每片迁移领域类型与规则、用例/端口、适配器映射、REST DTO，再删除旧路径；每片完成即跑编译与测试，不做平行双实现。
4. **分离传输、领域与持久化模型。** API 使用明确 DTO，application 使用命令/查询，domain 使用不可变值对象和有名业务类型，MyBatis/Flowable 专用模型封在适配器；映射集中并测试，移除通用实体继承和 `params` 魔法袋。
5. **明确失败、分页和事务边界。** 面向预期业务失败用 Java 21 sealed `Result`/错误代数类型传播，HTTP adapter 映射为标准 Problem Details；不可预期基础设施故障保留 cause 并在边界记录；分页变为显式输入/输出对象，事务只由 application 用例边界声明。
6. **重建工作流边界和数据契约。** 将 Flowable 调用收进 workflow adapter，通过端口驱动；明确模型草稿、部署版本、定义与业务流程键的关系；半天申请改用 `BigDecimal` 与数据库定点小数列；批量删除明确采用列表输入并逐项授权/校验；修复 multipart 的请求配置与集成验证。
7. **收敛并发与可观测性。** 移除自建 Kafka 轮询队列，按当前事件交付语义改为显式消息端口和受限执行器；需要可靠投递的事务事件使用 outbox，不需要时不额外引入；统一结构化日志、trace/MDC 传播、Micrometer 指标和异步失败记录，不将并行化当作默认装饰。
8. **前端升级到可静态验证的结构。** 将 Vue 2/Vue CLI 工程迁移为 Vue 3、TypeScript、Vite、Pinia；按业务 feature 切分页面、状态与 API，使用 OpenAPI 生成 TS 契约客户端；将 BPMN 编辑器封装为独立 adapter/component，修复请求 loading/error/finally、批量操作与上传语义。
9. **重建测试金字塔与文档。** 为纯领域规则、use case/port、MyBatis/Flowable 集成、HTTP 契约、前端组件及关键端到端流程增加测试；更新架构图、开发指南、运行配置与 SQL 初始化/迁移说明，删除过期模块路径。
10. **逐模块验收并清理旧架构。** 每一切片跑 Maven 校验和前端 lint/typecheck/unit/build；最终用架构测试确认依赖箭头，再全量执行验证。仅当新实现覆盖旧行为后删除旧类/依赖，不保留为兼容入口或影子实现。

## 关键决策（每项一句理由）

- **领域与应用层不依赖任何运行框架：** 这样业务规则可被普通单元测试验证，并能替换数据库、Web 框架或流程引擎。
- **REST、MyBatis、Flowable 都是外侧适配器：** 这样外部技术变更不再反向塑造业务接口。
- **采用不可变领域值对象与显式 sealed 结果：** 这样非法状态和预期失败尽量在编译期表达，不靠字符串约定或异常控制流。
- **不建通用 CRUD/万能 BaseService/共享万能响应：** 这些抽象会把本来不同的业务语义压平，而非减少真实复杂度。
- **选择 Java 21 与 Vue 3 + TypeScript：** 练手项目没有旧运行时约束，类型系统与现代语言能力可覆盖本次架构目标；具体依赖版本在基线核查后统一锁定。
- **并发按业务语义选择，而非全局并行：** 共享状态和数据库写操作并行会制造竞态，只有独立 I/O 或明确异步副作用才使用受限执行器/消息通道。

## 验收标准

- `domain` 与 `application` 编译依赖图中不存在 Spring、MyBatis、Flowable、Servlet、Redis/Kafka API。
- 不再存在 `AjaxResult`、`R<T>`、`Map` 作为通用业务响应；每个 API 有具名请求/响应类型和统一的错误协议。
- 领域入口无公开 setter；预期业务失败显式传播；数据库与 Flowable 映射不泄漏到 use case。
- 半天请假、工作流发起/审批/撤回、模型发布/部署、批量删除、上传等关键契约有测试覆盖。
- Maven 全量 verify、前端 lint/typecheck/unit/build 均通过，文档与最终模块/命令一致。

这是整体重构的执行蓝图，不是对现有代码的最终审计结论；计划模式要求先由你确认方案后才允许开始写入。
